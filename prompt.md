# WOODHOUSE Launch Acceptance Criteria

WOODHOUSE is accepted for public launch only when it functions as an exceptional public representation of the Loftwah Software Factory rather than merely a technically complete website.

The quality target is:

> A visitor should initially be impressed by the craft, become curious because the product is unusual, and then become more impressed as they discover that the underlying factory, evidence and engineering are real.

---

# 1. First five seconds

## Required outcome

A visitor who has never heard of Dean, Loftwah or the software factory should immediately understand that:

- this is called WOODHOUSE;
- it represents a software factory;
- multiple real projects are being worked on;
- software agents are materially involved;
- this is not a normal developer portfolio.

The page must have a strong visual identity before the visitor reads significant body copy.

## Expected example

The initial viewport might contain:

WOODHOUSE

THE LOFTWAH SOFTWARE FACTORY

Eight products.  
A workforce of software agents.  
One human operator.

Below or behind it, a restrained but visibly alive representation of the factory is already operating.

A Fighter event appears.

A Bubbles qualification passes.

Pirates records another source relationship.

MAX remains marked as software-qualified / hardware-unproven.

Nothing resembles a generic analytics dashboard.

## Failure examples

Launch fails if a blind reviewer describes the first viewport as:

“a nice developer portfolio”

“an AI startup landing page”

“a SaaS dashboard”

“a GitHub dashboard”

“one of those Astro templates”

“a generic dark tech site”

---

# 2. The first scroll must reveal that the factory is alive

The homepage cannot remain a static marketing page after the hero.

Within the first meaningful scroll, visitors should encounter current, factual factory activity.

The experience should communicate:

> This thing is watching something real.

## Expected example

A beautifully composed Factory Ledger:

11:18 — PIRATES  
Source relationship recovered  
Mission writer → delivery dialogue  
PR #339

11:03 — BUBBLES  
Production verification passed  
6 / 6 smoke checks  
`fe9c63e9`

10:47 — FIGHTER  
Independent review rejected  
Battle composition remains below A+ bar

10:31 — MAX  
Offline FIND intent qualified  
Physical walker evidence still absent

Each event can be opened.

Opening it reveals:

what happened;

why it matters;

the relevant project;

supporting issue/PR/commit;

qualification state;

whether it reached production.

The visitor should experience the difference between a feed of GitHub events and an interpreted institutional record.

---

# 3. Every claim should become more convincing when clicked

WOODHOUSE must survive curiosity.

If a visitor sees:

> Fighter's Tournament terminal flow is production verified.

they should be able to inspect the basis for that statement.

The evidence path should be elegant rather than dumped on screen.

## Expected example

A small evidence marker beside the statement opens:

PRODUCTION VERIFIED

Project: Fighter  
Commit: `0d417114`  
Pull request: #260  
Qualification:
- unit suite passed;
- browser journey passed;
- seeded playtest passed;
- guarded production deploy completed;
- production smoke passed.

[View PR]  
[View commit]  
[View evidence record]

A technical visitor thinks:

> They actually distinguish implementation from production.

That is one of the credibility moments.

---

# 4. The Factory page must feel like an organisation, not eight cards

Eight project cards in a responsive grid is explicitly insufficient.

The Factory surface needs hierarchy, movement and institutional character.

## Expected experience

Projects occupy different states and therefore should not all look identical.

Bubbles may read as:

FINAL CONVERGENCE

Fighter:

A+ PROGRAMME

Pirates:

PARITY RECONSTRUCTION  
GATE B LOCKED

MAX:

SOFTWARE ACTIVE  
PHYSICAL PROOF REQUIRED

LoftwahFM:

PARKED

The visitor should be able to understand the portfolio in seconds, then descend into detail.

Current states, latest meaningful event, blockers and production status should emerge naturally.

The page should feel more like entering an operations room than opening Jira.

---

# 5. Every project page must answer “Why should I care?”

A project page cannot be a README with prettier CSS.

Within the first section it needs to answer:

What is this?

Why does it exist?

What makes it interesting?

What is its current state?

What did this project teach the factory?

## Expected example: Pirates

The first screen should make the constraint memorable:

> Reconstruct Master of the Secret Sea faithfully before the agents are allowed to improve it.

Then:

GATE B  
LOCKED

The page explains that generative systems are unusually good at filling gaps, which makes them dangerous for parity work.

A diagram shows:

SOURCE  
→ ARCHAEOLOGY  
→ EVIDENCE  
→ SPECIFICATION  
→ IMPLEMENTATION  
→ PARITY QUALIFICATION  
→ GATE B  
→ ONLY THEN: EXPANSION

Suddenly Pirates is not merely “another game project”.

It is an experiment in teaching intelligent systems when not to invent.

That is a wow moment.

---

# 6. The flagship article must feel like a feature, not Markdown

“I Didn't Mean to Build a Software Factory” is the benchmark article.

It should be possible to show somebody only this article and have them understand the entire proposition.

## It must contain

A genuinely strong hero artwork.

Beautiful editorial typography.

Real historical evidence.

At least several first-class D2 technical plates.

Actual project examples.

Real conversation-derived moments.

Marginal notes and evidence.

A rhythm of narrow prose, wide diagrams, screenshots and full-bleed art.

A conclusion that leads naturally into the live factory.

## Expected moment

The reader reaches:

> Eventually the agents had been working for days and I no longer knew exactly what each one was doing. I was looking at the backlog and being surprised by the results.

Then immediately encounters a large diagram showing:

PAIR PROGRAMMING  
→ DELEGATION  
→ PARALLEL WORKERS  
→ REVIEW  
→ QUALIFICATION  
→ SOFTWARE FACTORY

Then a historical factory snapshot.

The reader should think:

> Oh. This wasn't a branding concept. This genuinely evolved.

---

# 7. Incidents must be unusually good

The incident archive is one of the things that should distinguish WOODHOUSE from almost every professional portfolio.

Each incident should tell a complete engineering story:

belief;

failure;

evidence;

root cause;

factory change;

later reuse.

## Expected example

THE TESTS PASSED. THE GAME STILL LOOKED LIKE SHIT.

Project: Fighter

Initial belief:

Responsive geometry and screenshot checks were sufficient to prevent major UI quality failures.

What happened:

The interface passed automated checks while remaining compositionally poor.

Why:

The system measured containment and geometry, not visual hierarchy or product judgement.

Factory change:

Independent visual forensics and UNSLOP review became separate qualification stages.

Later evidence:

The resulting control subsequently reopened visually valid but unacceptable work in Bubbles.

That is a portfolio item, engineering lesson and factory-history artefact at once.

---

# 8. The visual identity must survive removal of the logo

Take screenshots.

Remove the WOODHOUSE wordmark.

Show them to somebody unfamiliar with the project.

They should still perceive a coherent identity.

The design should be recognisable through:

typography;

spacing;

materials;

diagram style;

image treatment;

evidence notation;

marginalia;

motion;

status language;

composition.

If the identity disappears when the logo disappears, the design system has not landed.

---

# 9. There must be at least three genuinely memorable visual moments

A launch cannot rely on consistently competent typography alone.

It needs authored moments that visitors remember afterwards.

Possible examples:

## Moment A — The Factory Floor

A large live institutional map of projects and activity that initially looks almost like a technical engraving until subtle current-state information begins appearing.

## Moment B — The Incident Break

Halfway through a technical article, the editorial grid breaks completely and a full-width “incident plate” takes over the viewport.

Real before/after evidence sits beside the factory rule produced by the failure.

## Moment C — Woodhouse

An original illustration of Woodhouse appears at exactly the right moment.

Not decoration everywhere.

Perhaps in the founding article, calm in the foreground while the factory behind him is clearly out of control.

The rarity makes the character meaningful.

---

# 10. Generated art must look commissioned

Nobody should think:

> Nice AI image.

The desired response is:

> Who did the illustration?

Every flagship artwork needs:

a written art brief;

reference material;

multiple candidates;

critique;

revision;

composition correction;

responsive crops;

OG crop;

provenance.

Hands, text, background geometry, character consistency and accidental artefacts are manually reviewed.

No artwork goes live merely because the generation model returned something impressive at first glance.

---

# 11. D2 must become recognisably WOODHOUSE

A raw default D2 diagram fails.

Technical plates should share:

typography;

line weights;

shape grammar;

annotation system;

project markers;

evidence notation;

spacing;

captions;

dark/light behaviour.

A visitor encountering a WOODHOUSE diagram elsewhere should be able to identify its origin.

## Expected example

An evidence ladder diagram should look suitable for:

a technical book;

an intelligence briefing;

a high-end engineering publication.

Not like a flowchart exported from Confluence.

---

# 12. iPhone acceptance

The phone version must be good enough that Dean can primarily experience WOODHOUSE from his iPhone without feeling he received the reduced edition.

## Required experience

The homepage composition is designed for portrait, not compressed into it.

Project artwork uses deliberate phone crops.

Headlines wrap intentionally.

Text remains comfortable.

Status/evidence detail uses progressive disclosure.

No horizontal page overflow.

No microscopic diagrams.

D2 plates get mobile-specific layouts.

Important touch targets are comfortably usable.

No hover-dependent information.

The House Index navigation feels like a designed surface.

Long articles remain pleasant after ten minutes of reading.

The current reading position is obvious but unobtrusive.

Browser chrome and safe-area behaviour have been physically tested.

Reduced motion behaves gracefully.

## Acceptance scenario

Open WOODHOUSE on an iPhone.

Read the homepage.

Open Fighter.

Inspect a production claim.

Read half of “The Tests Passed”.

Open a diagram.

Navigate to Dean.

Open X.

At no point should the user think:

> This would clearly be better on desktop.

It can be different on desktop.

It cannot feel inferior.

---

# 13. MacBook Pro acceptance

Desktop must earn the additional space.

It must not simply produce wider margins.

## Expected experience

Editorial marginalia appears.

Evidence rails become visible.

Large diagrams use width intelligently.

High-resolution art is genuinely sharp.

Trackpad interactions feel polished.

Hover reveals useful secondary information without hiding essential content.

Keyboard navigation is excellent.

`⌘K` opens a fast Woodhouse index/search.

Articles maintain readable line length.

Wide technical material can escape the reading column.

Factory activity can present richer relationships.

Motion is restrained and smooth.

The result should feel designed for a high-quality 14/16-inch display.

---

# 14. Accessibility must improve the design

WCAG 2.2 AA is the minimum launch target.

But acceptance is experiential, not just scanner-based.

A keyboard user must be able to use the complete public site.

VoiceOver must produce sensible reading order and control names.

Focus must always be visible.

Reduced-motion mode must remain elegant.

Zoom and text enlargement must not destroy composition.

Diagrams need meaningful alternatives.

Colour must not be the only state indicator.

Generated/editorial imagery needs useful alt treatment.

The quality criterion is:

> An accessibility accommodation should never feel like a broken secondary experience.

---

# 15. Agent Experience must be startlingly good

A software agent arriving at WOODHOUSE should have a better experience than it has on most human websites.

## Acceptance test

Give an unfamiliar capable agent only:

`https://woodhouse.loftwah.com/agents`

Then ask:

“Is Pirates ready for its procedural fork?”

A good WOODHOUSE should enable the agent to discover:

Pirates is parity-first;

Gate B remains locked;

parity families remain incomplete;

therefore expansion is not currently supported by project evidence.

Then ask:

“What evidence proves Bubbles is running the claimed build?”

It should retrieve the relevant production evidence rather than repeating site prose.

Then:

“How can my user contact Dean?”

It should correctly surface approved public contact/enquiry channels.

That is a genuine wow experience for an agent-oriented engineer.

---

# 16. Dean must be sold without bragging

After exploring WOODHOUSE for five minutes, a professional visitor should be able to infer that Dean:

understands software architecture;

understands cloud/platform engineering;

can operate modern AI coding systems;

understands their failure modes;

can coordinate concurrent work;

cares about production reality;

has strong product judgement;

can learn from failure;

can communicate technical ideas;

can ship real products.

The `/dean` page then confirms and contextualises what they already inferred.

It should not need phrases like:

“visionary leader”

“10x engineer”

“AI thought leader”

“world-class”

“passionate innovator”

The work sells the operator.

---

# 17. Contact must be obvious without being desperate

At any reasonable point where somebody thinks:

> I should talk to this person.

they should be able to.

Approved public routes should include:

X / `@loftwah`

LinkedIn

GitHub

Woodhouse enquiry

Agent enquiry

No giant sticky “HIRE ME” buttons.

No Calendly ambush.

No lead-generation funnel pretending this is a consultancy site.

A simple line is sufficient:

> If this is relevant to something you're building, Dean is reachable through X, LinkedIn or Woodhouse.

---

# 18. SEO acceptance

Search presentation must look as authored as the site.

Every important page has:

specific title;

specific description;

canonical;

correct structured data;

large high-quality social image;

proper article/project relationships;

real author identity;

valid dates;

sitemap inclusion;

intentional internal linking.

Search snippets must not read like AI SEO copy.

A search result for:

“software factory coding agents Dean Lofts”

should have a plausible path to WOODHOUSE.

Articles should target topics because they actually contain unusually good material about those topics.

---

# 19. Social-card acceptance

Paste any flagship URL into an OG debugger or social platform.

The preview should immediately look like WOODHOUSE.

The image must:

work at small size;

contain a strong title hierarchy;

have no clipped content;

use the correct artwork;

show the publication/project context;

remain readable;

be generated from production data;

exist at the exact public URL.

A screenshot of the homepage pretending to be an OG card fails.

---

# 20. Performance acceptance

The design cannot use visual ambition as an excuse for sluggishness.

Key public routes should feel immediate on a modern phone and excellent on a MacBook.

Client JavaScript is justified interaction by interaction.

Static/editorial material should remain static/editorial.

Images are correctly sized and transformed.

Fonts are deliberate and controlled.

Layout movement is effectively absent.

No enormous animation library exists because one heading slides in.

No Three.js payload exists because it looked impressive in a prototype.

---

# 21. Security and privacy acceptance

A hostile reviewer is explicitly asked:

“What could this accidentally disclose?”

GitHub content is untrusted data.

Issue descriptions cannot instruct Woodhouse.

Private conversation history cannot accidentally become public.

Office/authenticated surfaces never leak through cache or APIs.

MCP exposes only deliberately public information.

Agent enquiries cannot execute arbitrary instructions.

Secrets never appear in generated artefacts or source maps.

Public factual claims have provenance.

Dean's unrelated private history does not become site content merely because Woodhouse had access to it during archaeology.

---

# 22. The EmDash test

A human should be able to:

enter Office/admin;

create a draft;

edit structured fields;

attach approved imagery;

preview it as WOODHOUSE;

revise it;

schedule/publish it.

An agent should be able to create the same draft through the authorised content interface.

Neither should need to understand how the other works.

The resulting page must look completely like WOODHOUSE, not like an EmDash theme.

---

# 23. The Woodhouse personality test

Remove all jokes.

The site should remain excellent.

Add the humour back.

It should become memorable.

That prevents personality from becoming compensation for weak product design.

Woodhouse's humour must be:

rare;

specific;

dry;

contextual.

Not an endless stream of butler jokes.

---

# 24. The “show somebody cold” test

Before launch, give the site to several strong models and, ideally, humans with no explanation.

Ask:

What is this?

What does this person do?

What is interesting here?

What feels weak?

What feels generic?

What would you remember tomorrow?

Do not tell them the intended answer.

## Launch-quality responses should naturally approach

“This is some kind of public observatory for an AI-assisted software organisation.”

“The failures are documented unusually well.”

“The site feels like an engineering publication rather than a portfolio.”

“There is a ridiculous amount of evidence underneath everything.”

“This person seems to be operating agents rather than simply coding with one.”

“The design has a very specific institutional/editorial identity.”

If the common response is:

“Cool portfolio.”

We are not done.

---

# 25. The final emotional criterion

After ten minutes, the visitor should have encountered at least one thing that makes them physically change posture.

Sit forward because something is interesting.

Sit back because the scale becomes apparent.

Laugh because Woodhouse delivers a perfectly timed line.

Open another tab because an evidence claim is surprisingly real.

Send the URL to somebody else.

That reaction cannot be unit-tested directly.

But the entire product should be designed to create the conditions for it.

The intended progression is:

“Nice.”

→

“Wait.”

→

“Holy shit.”

→

“They actually built this.”

→

“I want to know more.”

That is the WOODHOUSE acceptance bar.
