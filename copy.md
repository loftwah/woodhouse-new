## THE TESTS PASS. WOODHOUSE REMAINS UNCONVINCED.

An issue can close.

A pull request can merge.

A build can go green.

None of those things proves that the product is good, that the original intent was satisfied, or even that the code you think shipped is the code running in production.

The factory learned this repeatedly.

So Woodhouse keeps those claims separate.

**Implemented.**  
**Merged.**  
**Qualified.**  
**Production verified.**  
**Owner accepted.**

The distinction has been expensive enough to remember.

## I DIDN'T MEAN TO BUILD A SOFTWARE FACTORY

I started by gluing websites together with plugins.

A reverse proxy pointed at a VPS running WordPress. The useful skill was remembering what did each job best, collecting reusable capability and not rebuilding everything from scratch.

The tools changed.

WordPress plugins became APIs, cloud services, infrastructure modules, models, skills and agents.

Development became platform engineering.

Automation became delegation.

One coding agent became several.

Eventually the agents were working for days across multiple products and I needed another system just to explain what my own software factory had done.

That system is Woodhouse.

## INCIDENTS ARE NOT FOOTNOTES

The useful part of a failure is what changes afterwards.

Woodhouse records:

what we believed;

what actually happened;

why the existing controls missed it;

what rule changed;

and whether that rule caught the same class of problem somewhere else.

If the factory is learning, the history should show it.
