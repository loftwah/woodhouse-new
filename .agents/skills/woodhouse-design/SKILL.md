# Required design entry path — Woodhouse

This is a project routing rule, NOT the Impeccable skill, installer, design engine or proof of completion. Read the repository's AGENTS.md first and preserve its product, security, artwork, cost and delivery boundaries.

MP has already required Impeccable. Do not ask whether to use it and do not stop after recommending it or writing an issue.

1. Resolve the actual active harness and loaded Impeccable SKILL.md, version/revision, launcher and engine. Check project/global/plugin shadowing. Read the upstream skill and relevant references. Inspect current official releases; install/update through the supported route with reviewed versions, preserving customisations. The shared local helper is `scripts/impeccable-project.mjs`; read `docs/IMPECCABLE.md`. It can install and wire selected repositories but cannot certify design use. No moving remote script execution.
2. Verify real fresh-session discovery and supported design hooks. A model name is not a harness. Honour any genuine hook-trust approval; never mark an unapproved or unsupported hook active. Missing execution access remains an explicit blocker, not installation evidence.
3. Run the resolved context launcher once from this project's root for the target. Read current PRODUCT.md, DESIGN.md, surface briefs and accepted references. Use existing recorded owner decisions instead of asking MP to repeat them. Follow upstream fallback honestly if the launcher fails. Do not invent context or flatten this project's identity into a portfolio-wide theme.
4. Choose and READ the appropriate upstream playbook: shape/new-work, critique, audit, then targeted polish/adapt/harden/typeset/layout/clarify/optimise or another relevant operation. Read its craft floor before UI edits. These are agent workflows, not shell commands to invent. Detector-only use does not satisfy this requirement.
5. Inspect actual rendered pixels and interactions at representative phone/desktop sizes, keyboard/focus, contrast, overflow, loading/empty/error and reduced-motion states. Games need actual canvas/HUD/gameplay/touch inspection too. Repair material findings within authority, then inspect again. Respect real explicit holds; do not create arbitrary approval gates or needless redesigns.
6. Record source/target, effective tool/harness versions, context/playbooks, actual findings, changes or justified no-change, browser/interaction evidence and remaining limits in the existing project evidence/issue/PR. Keep setup, discovery, design use, remediation, integration and production verification separate. Deliver runtime changes through main and the authorised production path; tooling-only work needs main and focused checks, not an unrelated redeploy.
